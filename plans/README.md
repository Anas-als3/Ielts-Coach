## Dependency notes

- **001 blocks everything.** `src/profile/store.ts:76` returns `null` on a
  schemaVersion mismatch, `loadSessions()` turns that into `[]`, and
  `saveSession()` then overwrites the key with that empty list plus one record.
  Any schema bump therefore silently destroys a learner's entire history. Plans
  003–005 all require `SessionRecord.task`, which needs schemaVersion 2. Landing
  003 before 001 would ship the data-loss bug to every existing user.
- **002 is independent** of the Task 1 sequence and can run at any time,
  including in parallel. It is sequenced second only because it is small and
  makes plan 004's complexity-marker reuse cleaner. If 002 has not landed when
  004 runs, 004 has a documented fallback.
- **003 → 004 → 005 is a strict chain.** 004 imports `deriveChartFacts` and
  `TASK1_PROMPTS` from 003; 005 imports `analyzeTask1` and `criterionLabel` from
  004.
- Suggested split if parallelising: one executor on 001 → 003 → 004 → 005, a
  second on 002.

## The four stages, assessed

Ranked by fit with the app's stated moat — deterministic, offline, no LLM, no
server (`SPEC.md:8-12`).

| Stage | Fit | Verdict |
|---|---|---|
| **Task 1 Academic** | Excellent. Same text medium; `cohesion.ts`, `lexical.ts`, `grammarRange.ts` and `accuracy.ts` apply unchanged. Same four criteria (Task Achievement occupies the Task Response slot). | **Planned — 003/004/005** |
| **Reading** | Perfect engine fit but the engine is trivial: answer key → raw score → band conversion. The cost is authoring passages and 40-question sets, plus per-question-type accuracy tracking. | Build after Task 1 |
| **Speaking Part 2 (notes-only)** | Partial. Full Speaking needs ASR (Chrome-only, breaks offline-first) and Pronunciation is unscorable by rules. The honest deterministic slice is the cue-card drill: 1-min prep, typed notes, 2-min self-timed talk, coverage checked against the card's four bullets. ~4–5 days. | Viable slice, not planned yet |
| **Listening** | Blocked on authored audio — the same wall as Speaking, plus content production. | Defer |

**Why Task 1 is the unlock.** A rule engine cannot read a chart image, which is
why `SPEC.md:196` cut Task 1 from v1. The way around it is to *author the data*:
each prompt carries its chart as structured numbers, the app renders the SVG
itself, and the engine gains factual checking no competitor has deterministically
— "you wrote 47%, but no value in this chart is 47", "you never stated an
overview". That is only possible because the app owns the numbers.

## Findings considered and rejected

So nobody re-audits these:

- **The `complex-count` rail check requiring one marker per paragraph** — reported
  as a false negative by the user (an essay with 4 of 4 markers still showed
  unchecked because the introduction and conclusion had none). Working exactly as
  specified at `SPEC.md:254-257`; the per-paragraph requirement is deliberate and
  IELTS-defensible. Not a bug. The genuinely wrong part — `\bafter\b` matching
  inside `after-school` — is covered by plan 002.
- **Extending `Criterion` to five members for Task Achievement** — considered and
  rejected in plan 004's design section. IELTS marks one slot under two names;
  a fifth member would force `Partial<Record<Criterion, …>>` through
  `bandEstimate.ts`, `Report.tsx`, `FeedbackPanel.tsx` and `meta.ts` for no gain.
  Task 1 reuses the `TR` slot with a task-aware label.
- **Widening `RuleFn` to accept a Task 1 prompt** — rejected in plan 003. It
  would ripple through six rule modules so that four of them could ignore the
  new shape. `task1AchievementRules` takes its own signature instead.
- **Adding a chart library** — rejected. "No runtime dependencies beyond React"
  is a stated architectural property (`README.md:67`). The renderer is
  hand-written SVG.
- **Supporting Task 1 map questions** — deliberately out of scope. A map cannot
  be expressed as `categories × series` and needs a different renderer and
  different rules. Separate work.
- **Merging the two complexity-marker word lists** — explicitly forbidden in
  plan 002. Both are canonical in SPEC.md, and merging would move the band
  calibration anchors at `SPEC.md:160-161` and the rail check simultaneously.
  Plan 002 single-sources them while keeping both.

## Known limitations carried forward

Recorded here so they are not rediscovered as findings:

- **The error profile does not scope by task.** `computeProfile` and
  `computeTrends` aggregate `IssueCategory` counts across all sessions. Correct
  for LR/GRA categories (those skills transfer), wrong for TR/CC and every
  `t1-*` category. `SessionRecord.task` (plan 001) is the hook. Do this before
  adding a third task. Noted in plans 001, 004 and 005.
- **No jsdom or component tests.** Plan 005's gate is a 10-point manual
  checklist, which will not scale. Adding `environment: 'jsdom'` plus
  `@testing-library/react` and converting that checklist into render tests is
  the right next investment.
- **The band trend chart mixes tasks.** Plan 005 adds a disclosing caption; the
  real fix is two series or a task filter.
- **No Task 1 cheat sheet.** `CheatSheet.tsx` is Task 2 content and is hidden in
  Task 1 rather than replaced.
